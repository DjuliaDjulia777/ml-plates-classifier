# Model_retrain_BPMN: Процесс автоматического переобучения модели

## 1. Описание процесса
Данный документ описывает жизненный цикл ML-модели, начиная с момента, когда она требует обновления, и заканчивая ее публикацией в production. Процесс реализуется с использованием практик **MLOps**.

## 2. Основные этапы процесса

### 1. Триггер запуска переобучения
Процесс запускается автоматически или вручную при наступлении одного из событий:
- **Data Drift:** статистические характеристики входных данных (например, освещение, новые типы тарелок) изменились по сравнению с обучающей выборкой.
- **Model Drift (деградация):** точность модели на живом трафике упала ниже установленного порога (например, Accuracy < 90%).
- **Расписание:** плановое переобучение раз в месяц (по крону).
- **Ручной запрос:** Data Scientist выявил проблему.

### 2. Получение и подготовка новых данных
- Сбор новых изображений из production (с согласия и с удалением персональных данных, если применимо).
- Разметка данных (если используется подход Active Learning).
- Очистка данных, удаление дубликатов (Data Leakage Prevention).
- Разделение на Train/Val/Test.

### 3. Обучение новой версии модели
- Запуск пайплайна обучения с использованием подготовленных данных.
- Использование тех же гиперпараметров или запуск Hyperparameter Tuning (Optuna).
- Сохранение артефактов (веса модели, конфиги, логи).

### 4. Проверка качества модели
- Валидация на отложенной тестовой выборке.
- Сравнение метрик с текущей production-версией (Champion vs Challenger).
- Проверка на устойчивость (Robustness testing, Adversarial testing).

### 5. Принятие решения о возможности публикации новой версии
- Шлюз (Gateway): Если метрики новой модели **лучше** текущей (например, F1-score вырос) и пройдены все проверки — модель одобряется. В противном случае — возвращается на доработку.

### 6. Регистрация или сохранение новой версии модели
- Версионирование модели (например, `v2.1.0`).
- Сохранение в Model Registry (MLflow, DVC).
- Логирование метаданных (дата, автор, датасет, метрики).

### 7. Деплой модели
- Упаковка модели в Docker-контейнер.
- Выкатка (Rollout) на staging-сервер.
- Канареечный релиз (Canary release) — 5% трафика направляется на новую модель для проверки в реальных условиях.

### 8. Мониторинг (Обратная связь)
- Сбор метрик инференса.
- Логирование предсказаний.
- Отслеживание дрифта.

## 3. Схема процесса (PlantUML)

*Код для рендеринга схемы (planttext.com).*

```plantuml
@startuml
skinparam ActivityBackgroundColor #E3F2FD
skinparam ActivityBorderColor #2196F3

start
:Триггер переобучения\n(Drift / Расписание);
:Сбор и подготовка данных;
:Обучение новой версии модели;
:Проверка качества;

if (Новая модель лучше текущей?) then (Да)
  :Регистрация в Model Registry;
  :Сохранение артефактов;
  :Деплой на Staging;
  :Канареечный релиз (5%);
  if (Метрики в порядке?) then (Да)
    :Полный деплой в Production;
  else (Нет)
    :Откат (Rollback);
  endif
else (Нет)
  :Отклонение модели;
endif

:Мониторинг и сбор логов;
stop
@enduml
